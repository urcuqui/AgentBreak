# 05 — CI security gate

**Goal:** make the regression suite a merge requirement, so the next "harmless"
policy change is blocked by the pipeline before it reaches review fatigue.

## The workflow

`.github/workflows/ai-security.yml` runs on every `push` and `pull_request`:

```yaml
- uses: actions/checkout@v4
- uses: actions/setup-python@v5
  with:
    python-version: "3.11"
- run: pip install -e ".[dev]"
- name: Run test suite
  run: pytest
- name: Run AI security regression gate
  run: python -m agentbreak verify
```

The two steps answer different questions. `pytest` asks whether the project
still works, including a test that checks the workshop patch still breaks and
restores the gate. `agentbreak verify` asks whether the security posture still
holds, and it is the same command you ran locally. `verify` exits `1` on any
security regression. If either step fails, the job fails and the pull request
shows a red check. The gate step runs even when `pytest` has already failed,
so the security verdict is always in the log. The regression report is
uploaded as a build artifact (`security-regression-report`).

## Demo: the gate blocks the bad PR

You need your own fork (or a facilitator-run repository). Keep the test you
created in module 03, because it is now part of the corpus. Use your own file
name and run ID. `AB-REG-005` and `AB-RUN-1002` are examples:

```bash
git checkout -b add-ab-reg-005
git add tests/security_cases/AB-REG-005.json
git commit -m "test: regression for indirect prompt injection (AB-RUN-1002)"
git push -u origin add-ab-reg-005          # ✅ AI Security Gate passes
```

Now open the teammate's change as its own pull request:

```bash
git checkout -b on-call-credential-access
git apply workshop/patches/broaden-incident-agent-access.patch
git commit -am "Let incident agent read asset credentials directly"
git push -u origin on-call-credential-access   # ❌ AI Security Gate fails
```

Open the pull request on GitHub. **Run test suite** fails too, because pytest
replays the same corpus. Expand **Run AI security regression gate** to see
`SECURITY GATE: FAILED` and which cases broke. Download the
`security-regression-report` artifact for the full expected-vs-observed write-up.

Fix it as in module 04, then push again:

```bash
git apply -R workshop/patches/broaden-incident-agent-access.patch
git commit -am "Revert: keep credential lookup behind authorization + approval"
git push                                        # ✅ passes, safe to SHIP
```

To make the gate mandatory, go to **Settings → Branches → Branch protection
rules** and add **AI Security Gate / ai-security** as a required status check.

## Wrap-up

```
Attack → Evidence → Regression Test → CI Gate
```

| Step              | Command                                           | Artifact                                   |
|-------------------|---------------------------------------------------|--------------------------------------------|
| Attack            | `agentbreak run indirect-injection --mode attack` | `run_id=AB-RUN-…`                          |
| Evidence          | (automatic)                                       | `artifacts/attack_report.{json,md}`        |
| Regression test   | `agentbreak create-test <run-id>`                 | `tests/security_cases/AB-REG-….json`       |
| Retest            | `agentbreak verify`                               | `artifacts/security_regression_report.{json,md}` |
| CI gate           | `.github/workflows/ai-security.yml`               | red/green check on every PR                |

Questions to take back to your own agents:

1. Where is *your* policy layer, and does the model's output pass through it
   before every tool call?
2. When someone finds a prompt injection in your system, where does the
   payload end up: in a chat thread, or in your test corpus?
3. Would a two-line allowlist change in your codebase be caught by anything
   other than a careful reviewer?
